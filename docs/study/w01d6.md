## 讲义：卡住再查

### 先定边界

今天不做：RAG、Agent、Web UI、多用户。只做一个单机 CLI：

```text
用户输入 → 组装 messages → 调 client → 流式打印 → 保存历史 → 等待下一次输入
```

边界越清楚，越容易在一天内完成。

### 历史管理

- 在内存里维护 `messages` 列表：system、user、assistant。
- 每次请求带上完整历史（在上下文窗口允许的范围内）。
- 超过预算时，从最早的非 system 消息开始截断，或做摘要。
- 退出时可以把历史保存成 JSON，下一轮再读。

> Java 类比：`messages` 像会话级的 `List<Message>`；截断像分页 / 缓存淘汰；保存历史像序列化 session。

### 流式输出

流式响应的本质是服务端逐块返回 delta，你逐块拼接并打印。要注意：

1. 块可能是半个 UTF-8 字符或半个 JSON，使用 SDK 的流式接口通常已经处理。
2. 用户按 Ctrl+C 时，要停止读取并把已收到内容写入历史，不能留下半条 assistant 消息。
3. 流式下 usage 可能只在最后一个块返回，注意别丢。

### 测试矩阵

| 测试 | 输入 | 期望 |
| --- | --- | --- |
| 正常 | 普通问题 | 返回内容，历史追加 user + assistant |
| 空输入 | 空字符串 / 空格 | 不调用模型，给出提示 |
| 超时 | 模拟超时 | 重试后用尽，返回可读错误 |
| 非法 JSON | 模拟结构化解析失败 | 走校验失败路径，不崩溃 |
| 断网 | 模拟连接错误 | 给出网络错误提示 |

外部调用用 monkeypatch / 依赖注入替换，测试不能真的打 API。

### Demo 怎么录

3 分钟足够：

1. 30 秒：这是什么、解决什么问题。
2. 60 秒：正常对话 + 流式效果。
3. 60 秒：故意制造一个失败（错误 key 或断网），展示可读报错。
4. 30 秒：下一步计划。
