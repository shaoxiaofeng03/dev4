## 讲义：卡住再查

### 最小调用长什么样

大多数兼容 OpenAI 的 API 都是同一个形状：向 `/chat/completions` POST 一个 JSON，带上 `model`、`messages`，从响应里取第一个 choice 的 content。

你要写的客户端至少要有：

1. 配置：从环境变量读 `LLM_BASE_URL`、`LLM_API_KEY`、`LLM_MODEL`。
2. 请求：`messages` 数组、`temperature`、`max_tokens`。
3. 响应：取 content，同时记录 usage 里的 input / output tokens。
4. 错误：把 HTTP 状态码和响应体一起带出来，不要只抛一个 `Exception`。

> Java 类比：这层相当于 `RestTemplate` / `WebClient` 的封装，但外部依赖是概率模型，所以错误处理和重试比普通 HTTP 服务更重要。

### 超时与重试

- **连接超时**：TCP 都连不上，通常是网络问题。
- **读取超时**：连上了但模型迟迟不返回，可能是排队或生成很长。
- 建议设置总超时（例如 30–60 秒），并根据场景调整。

重试策略：

- 只对**可重试**错误重试：超时、连接错误、429、5xx。
- 不要对 400 / 401 / 403 重试，重试也不会变对。
- 用指数退避 + 随机抖动，避免同时打爆服务。
- 设最大次数（2–3 次），并记录每次重试。

> Java 类比：`Resilience4j` 的 Retry + TimeLimiter。区别是要先做错误分类，否则会把「参数写错」也重试三遍。

### 三种必须亲手制造的失败

1. **断网**：关掉网络或把 base_url 改成不可达地址。期望：连接错误，重试后给出可读提示。
2. **错误 key**：换一个无效 key。期望：401，不重试，提示检查配置。
3. **超时**：把超时设成 1 毫秒，或让服务端变慢。期望：超时错误，重试次数用尽后返回。

记录成一张表：场景 / 错误类型 / 重试次数 / 最终提示。这张表就是本周交付的一部分。
